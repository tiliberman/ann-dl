    Reprodutibilidade

    A divisão usa o gerador que o enunciado fixa, e torch.manual_seed(42) roda logo antes de cada modelo ser construído (dentro de train_vae). Rodando

    pip install -r requirements.txt
python docs/exercises/vae/code/exercises.py

    a partir da raiz do repositório (cerca de 15 min numa CPU; o MNIST é baixado em data/ uma vez), os números desta página são impressos e todas as figuras são regeradas em figures/. Os números foram obtidos com Python 3.12.10, PyTorch 2.15.0 (CPU), torchvision 0.29.2, NumPy 2.5.3, SciPy 1.18.1, scikit-learn 1.7.2 e Matplotlib 3.11.2.

    O script fixa torch.set_num_threads(1), porque o número de threads muda o arredondamento e, com ele, a trajetória do treino: repetir a execução dá pesos idênticos, mas com a mesma semente e 4 ou 16 threads (basta trocar esse valor no script) a rede de \(d = 16\) termina com reconstrução de 81,74 ou 81,81 no teste, contra 80,41 aqui. Uma CPU com outro conjunto de instruções pode ter o mesmo efeito. Diferenças dessa ordem (1 a 2 nats) não são resultado.

    O fio condutor é o cabo de guerra dentro da perda. Um VAE paga por duas coisas: reconstruir a entrada e manter o espaço latente perto de um prior do qual se possa amostrar. O Exercício 1 registra os dois termos em separado e mostra por que vale a pena pagar KL. O Exercício 2 reduz o espaço latente a duas dimensões, para ver o que o prior compra e quanto custa.

    def to_matrix(dataset):
    """Flatten a (sub)set of MNIST into an N x 784 matrix in [0, 1] and a vector of labels."""
    images, labels = zip(*dataset)
    return torch.stack(images).flatten(1), torch.tensor(labels)


def load_mnist():
    """The split exactly as the statement fixes it."""
    train_full = datasets.MNIST("data", train=True, download=True, transform=transforms.ToTensor())
    test = datasets.MNIST("data", train=False, download=True, transform=transforms.ToTensor())
    train, val = random_split(train_full, [50_000, 10_000],
                              generator=torch.Generator().manual_seed(42))
    return to_matrix(train), to_matrix(val), to_matrix(test), train.indices[:5]

    class VAE(nn.Module):
    """Encoder 784 -> 512 -> 256, two heads 256 -> d, decoder d -> 256 -> 512 -> 784."""

    def __init__(self, d):
        super().__init__()
        self.d = d
        self.encoder = nn.Sequential(
            nn.Linear(784, 512), nn.ReLU(),
            nn.Linear(512, 256), nn.ReLU(),
        )
        # Two heads on the same 256 features. The second predicts log(sigma^2) and not sigma
        # because a linear layer is unbounded and a variance must be positive: exp() of any
        # real number is a valid variance, with no clipping.
        self.mu_head = nn.Linear(256, d)
        self.logvar_head = nn.Linear(256, d)
        # The sigmoid makes each output a Bernoulli probability, "the pixel is on".
        self.decoder = nn.Sequential(
            nn.Linear(d, 256), nn.ReLU(),
            nn.Linear(256, 512), nn.ReLU(),
            nn.Linear(512, 784), nn.Sigmoid(),
        )

    def encode(self, x):
        """Parameters of q(z | x), a diagonal Gaussian: mu and log(sigma^2), each N x d."""
        h = self.encoder(x)
        return self.mu_head(h), self.logvar_head(h)

    def decode(self, z):
        """Pixel probabilities of p(x | z), N x 784. This is the mean of p(x | z), not a draw."""
        return self.decoder(z)

    Reparametrização e os dois termos da perda, escritos à mão:

    \[ \mathbf{z} = \mu + \sigma \odot \epsilon, \quad \epsilon \sim \mathcal{N}(0, I); \qquad L = \underbrace{-\sum_{j=1}^{784} \left[x_j \log \hat{x}_j + (1 - x_j)\log(1 - \hat{x}_j)\right]}_{\text{reconstrução}} + \beta\, \underbrace{\tfrac{1}{2}\sum_{i=1}^{d}\left(\mu_i^2 + \sigma_i^2 - 1 - \log \sigma_i^2\right)}_{\text{KL}} \]

    com \(\beta = 1\) e a média sobre as imagens do lote. A amostragem é sample_prior: sorteia \(\mathbf{z} \sim \mathcal{N}(0, I)\) e decodifica.

    def reparameterize(mu, logvar, generator=None):
    """z = mu + sigma * eps, eps ~ N(0, I): the noise enters as data, so gradients reach both heads.

    With generator=None the noise comes from the global torch stream (training). Evaluation
    passes its own generator, so measuring a model never changes how the training continues.
    """
    sigma = torch.exp(0.5 * logvar)  # sigma = exp(log(sigma^2) / 2)
    eps = torch.randn(mu.shape, generator=generator)
    return mu + sigma * eps


def reconstruction_term(x_hat, x):
    """-log p(x | z) under a Bernoulli per pixel: BCE summed over the pixels, averaged over images.

    reduction="sum" followed by the division is the point: reduction="mean" would also divide by
    784 and shrink this term relative to the KL, which amounts to a hidden beta of about 784.
    """
    return F.binary_cross_entropy(x_hat, x, reduction="sum") / x.size(0)


def kl_term(mu, logvar):
    """KL( N(mu, sigma^2) || N(0, I) ) in closed form, summed over d, averaged over images:

        1/2 * sum_i ( mu_i^2 + sigma_i^2 - 1 - log(sigma_i^2) )
    """
    return 0.5 * torch.sum(mu.pow(2) + logvar.exp() - 1.0 - logvar) / mu.size(0)


def sample_prior(model, n, generator=None):
    """Generation: draw z ~ N(0, I), n x d, and decode it. The encoder takes no part."""
    return model.decode(torch.randn(n, model.d, generator=generator))

    def check_hand_written_parts():
    rng = generator(100)

    # BCE: F.binary_cross_entropy against the formula of the statement, written out.
    x = torch.rand(32, 784, generator=rng, dtype=torch.float64)
    p = torch.rand(32, 784, generator=rng, dtype=torch.float64).clamp(1e-3, 1 - 1e-3)
    written_out = -(x * p.log() + (1 - x) * (1 - p).log()).sum(1).mean()
    print(f"   BCE, formula {written_out.item():.6f} | reconstruction_term {reconstruction_term(p, x).item():.6f}")
    print("   reduction='mean' x 784 equals the summed term:",
          f"{784 * F.binary_cross_entropy(p, x, reduction='mean').item():.6f}")

    # KL: zero at the prior, and the closed form against a Monte Carlo estimate of the definition
    # E_q[log q(z) - log p(z)], with both densities written out.
    print(f"   KL at mu = 0, log(sigma^2) = 0: {kl_term(torch.zeros(8, 16), torch.zeros(8, 16)).item():.6f}")
    mu = torch.randn(4, 16, generator=rng, dtype=torch.float64)
    logvar = torch.randn(4, 16, generator=rng, dtype=torch.float64) - 1.0
    eps = torch.randn(200_000, 4, 16, generator=rng, dtype=torch.float64)
    z = mu + torch.exp(0.5 * logvar) * eps
    log_q = -0.5 * (eps.pow(2) + logvar + LOG_2PI).sum(-1)
    log_p = -0.5 * (z.pow(2) + LOG_2PI).sum(-1)
    samples = (log_q - log_p).mean(1)  # per draw, averaged over the 4 images
    print(f"   KL, closed form {kl_term(mu, logvar).item():.4f} | Monte Carlo {samples.mean().item():.4f}"
          f" (standard error {samples.std().item() / math.sqrt(len(samples)):.4f})")

    # Reparameterization: autograd must reproduce dz/dmu = 1 and dz/dlogvar = sigma * eps / 2.
    mu = torch.tensor([0.5, -1.0, 2.0], requires_grad=True)
    logvar = torch.tensor([-1.0, 0.0, 0.7], requires_grad=True)
    reparameterize(mu, logvar, generator(101)).sum().backward()
    eps = torch.randn(3, generator=generator(101))
    expected = 0.5 * torch.exp(0.5 * logvar.detach()) * eps
    print(f"   reparameterization, max |dz/dmu - 1| = {(mu.grad - 1).abs().max().item():.2e},"
          f" max |dz/dlogvar - sigma eps / 2| = {(logvar.grad - expected).abs().max().item():.2e}")

    def train_vae(d, x_train, x_val, beta=1.0, lr=1e-3, batch_size=128, epochs=20):
    """Train one VAE with latent dimension d. Returns the model and the history of both terms."""
    torch.manual_seed(42)  # before building each model, as the statement fixes it
    model = VAE(d)
    optimizer = torch.optim.Adam(model.parameters(), lr=lr)
    loader = DataLoader(TensorDataset(x_train), batch_size=batch_size, shuffle=True)
    # A separate stream for the validation draws: the global stream, which drives the shuffling
    # and the training noise, is the same whether or not validation runs.
    val_generator = torch.Generator().manual_seed(1)

    history = {key: [] for key in ("train_rec", "train_kl", "val_rec", "val_kl", "batch_rec", "batch_kl")}
    # "Epoch 0": the untrained network on the validation set, as the starting point of the curves.
    history["val_rec_init"], history["val_kl_init"] = evaluate(model, x_val, val_generator)

    start = perf_counter()
    for epoch in range(1, epochs + 1):
        rec_sum, kl_sum = 0.0, 0.0
        for (x,) in loader:
            mu, logvar = model.encode(x)
            z = reparameterize(mu, logvar)
            x_hat = model.decode(z)

            # Each term on its own: a total that falls says nothing about which term is winning.
            rec = reconstruction_term(x_hat, x)
            kl = kl_term(mu, logvar)
            loss = rec + beta * kl

            optimizer.zero_grad()
            loss.backward()
            optimizer.step()

            # Epoch average weighted by batch size (the last of the 391 batches has 80 images).
            rec_sum += rec.item() * x.size(0)
            kl_sum += kl.item() * x.size(0)
            history["batch_rec"].append(rec.item())
            history["batch_kl"].append(kl.item())

        history["train_rec"].append(rec_sum / len(x_train))
        history["train_kl"].append(kl_sum / len(x_train))
        val_rec, val_kl = evaluate(model, x_val, val_generator)
        history["val_rec"].append(val_rec)
        history["val_kl"].append(val_kl)

    history["seconds"] = perf_counter() - start
    return model, history

    E — Analysis

    Por que o otimizador paga mais KL. Porque ele minimiza a soma, e o KL é o preço de o código dizer alguma coisa sobre a imagem. Na validação, entre a primeira e a última época, o KL sobe de 13,47 para 20,29 enquanto o total cai de 143,03 para 101,35.

    Sem informação em \(\mathbf{z}\), o decodificador não tem como distinguir as imagens: o melhor que ele pode fazer é devolver sempre a média do treino, que dá reconstrução de 205,60 na validação, com KL 0. A Figura 1b mostra a rede passando por esse patamar: depois de um transiente (pico de KL de 17,04 na iteração 10), entre as iterações 21 e 40 ela tem reconstrução de 212,31 e KL de 0,15. Daí em diante, pôr informação no código compensa. Ainda na primeira época, entre as iterações 41–60 e 372–391, o KL passa de 1,12 para 12,92 e a reconstrução de 203,97 para 131,40: 11,80 nats pagos, 72,57 economizados. Da imagem constante até a época 20, são 124,55 economizados e 20,29 pagos, 6,14 por nat.

    Essa conta é uma média, não o preço do último nat, e mistura o ganho da informação com o decodificador melhorando ao mesmo tempo. Com \(\beta = 1\), pagar mais deixa de compensar quando o próximo nat devolve só um nat de reconstrução. Por isso o KL não sobe para sempre: a partir da época 10 ele quase para (19,46 na época 10, 20,29 na época 20), embora a reconstrução siga caindo (de 85,42 para 81,05).

    Por que a Figura 3 é pior que a Figura 2. Razão 1: onde as amostras do prior caem. Os códigos das imagens têm a variância do prior, mas não a sua forma. A variância agregada de cada dimensão, \(\text{Var}[\mu_i] + \mathbb{E}[\sigma_i^2]\), está entre 0,97 e 1,09, tal como a do prior, mas a nuvem é agrupada por dígito: um k-NN (\(k = 15\)) lê o dígito a partir de \(\mu\) com 96,51% de acerto. \(\mathcal{N}(0, I)\) é uma única bolha, e muitas das suas amostras caem entre os grupos, onde o decodificador produz algo intermediário, ou nenhum dígito.

    @torch.no_grad()
def code_sets(model, x_train, y_train, x_val, K=2000):
    """The same decoder is fed codes of different origins: only where z lands changes."""
    mu_train, logvar_train = model.encode(x_train)
    z_train = reparameterize(mu_train, logvar_train, generator(30))
    ids = torch.randperm(len(x_val), generator=generator(7))[:K]
    mu_val, logvar_val = model.encode(x_val[ids])

    def gaussian_like(codes, n, rng):
        """A Gaussian with the mean and the full covariance of these codes."""
        cholesky = torch.linalg.cholesky(torch.cov(codes.T))
        return codes.mean(0) + torch.randn(n, model.d, generator=rng) @ cholesky.T

    # First a digit, with its frequency in training, then a Gaussian fitted to that digit's codes.
    digits = y_train[torch.randint(len(y_train), (K,), generator=generator(33))]
    per_digit = torch.cat([gaussian_like(z_train[y_train == k], int((digits == k).sum()), generator(40 + k))
                           for k in range(10)])
    return ids, {
        "z = mu, validation": mu_val,
        "z ~ q(z|x), validation": reparameterize(mu_val, logvar_val, generator(8)),
        "one Gaussian per digit": per_digit,
        "one Gaussian fitted to the codes": gaussian_like(z_train, K, generator(32)),
        "z ~ N(0, I), the prior": torch.randn(K, model.d, generator=generator(9)),
    }

Ele serve para comparar conjuntos de imagens decodificadas, não como juízo absoluto de "é um dígito".

    Acertar a variância e as correlações quase não ajuda (46,8% contra 48,6%), e sortear de dentro de um grupo resolve a maior parte (16,9%). O problema, portanto, não é a escala: é a estrutura em grupos. Na grade da própria Figura 3, 32 de 64 imagens ficam abaixo de 0,9 e 4 de 64 abaixo de 0,5. O KL é o que traz o prior para perto dos códigos: sem ele (\(\beta = 0\)), a variância agregada fica entre 8,68 e 18,82, e 99,6% das amostras do prior ficam abaixo de 0,9.

    Razão 2: o que o decodificador devolve para um dado \(\mathbf{z}\). A saída não é uma imagem sorteada do modelo: é a média de \(p(\mathbf{x} \mid \mathbf{z})\), uma probabilidade por pixel. Para um \(\mathbf{z}\) fixo, a BCE esperada é mínima em \(\hat{x}_j = \mathbb{E}[x_j \mid \mathbf{z}]\). Como diz a seção da aula sobre o borrão, se várias imagens nítidas são compatíveis com um código, a saída ótima é a média delas, e médias de imagens são borradas. A Figura 5b mostra essa média diretamente, em \(d = 2\).

    Essa razão vale nas duas figuras: mesmo em \(\mathbf{z} = \mu\), os pixels cinza sobem de 67,3 nas imagens reais para 113,1. E parte desse cinza é indecisão: dos 113,9 pixels cinza da saída (em toda a validação), 59,0 são cinza também na imagem real, as bordas do traço, e 54,8 são quase pretos ou brancos na imagem real. As duas razões se combinam assim: a razão 2 explica por que nada, nas duas figuras, é nítido; a razão 1 explica o que a Figura 3 tem a mais, os não-dígitos e o borrão extra (131,1 pixels cinza no prior contra 113,6 em \(q\), com o mesmo decodificador).

    Por que decodificar \(\mu\) na Figura 2. Porque a figura pergunta o que o modelo guardou desta imagem, e \(\mu\) é a resposta: o centro de \(q(\mathbf{z} \mid \mathbf{x})\), um único código por imagem, sem sorteio. O ruído \(\sigma\epsilon\) existe para treinar e para estimar a ELBO, não para descrever a imagem, e ele não é pequeno. Na validação, dois sorteios de \(\mathbf{z}\) para a mesma imagem decodificam para imagens a 1,82 de distância uma da outra (norma euclidiana, em média), contra 2,85 entre a imagem original e a decodificação de \(\mu\). Sortear também piora o resultado: a reconstrução é de 75,57 nats com \(\mu\) e 81,05 com \(\mathbf{z}\) sorteado, pior em 94,8% das imagens.

Dois números e um decodificador suave formam uma folha de duas dimensões em \(\mathbb{R}^{784}\): códigos vizinhos têm de dar imagens parecidas, e cada lugar do plano tem uma única imagem.     A Figura 5 é a evidência. Andar pelo plano é a única forma de variar o estilo, e essa variação acontece junto com a troca de dígito. A inclinação coube: nas duas primeiras linhas, os 1 giram continuamente de \(z_1 = -1{,}64\) até \(z_1 = 0\), e, medindo as próprias células, separadas por classe, o desvio da inclinação é quase o real (0,228 contra 0,261). A tinta coube bem menos: 16,28 contra 27,47. E nenhuma célula é tão nítida quanto uma imagem original. A Figura 5b mostra os dois efeitos juntos: dez imagens de traços bem diferentes para um só código, e uma única saída de traço médio.

    O limite é a folha, não o KL. O KL baixo de \(d = 2\) poderia parecer a causa, mas o controle sem KL mostra que não é:

    Modelo KL (teste) Reconstrução (teste) Erro quadrático de \(\mu\) (validação)
    \(d = 2\), \(\beta = 1\) 6,76 133,92 28,43
    \(d = 2\), \(\beta = 0\) 77,03 132,69 28,18
    \(d = 16\), \(\beta = 0\) 302,96 67,15 6,36

    Sem KL, o código pode ser mais de 11 vezes mais caro, e a reconstrução quase não muda (de 133,92 para 132,69). Nos dois números não cabe mais do que isso, com ou sem KL. O KL baixo é consequência: de nada adianta um código mais preciso que o decodificador não consegue aproveitar. Sem KL em nenhum dos dois, ir de \(d = 2\) para \(d = 16\) ainda vale 65,54 nats: é o custo das dimensões que faltam.

    Qual linha da Figura 6 passa por dígitos. A de baixo, a do espaço latente: cada quadro é um único traço, que se deforma do 3 ao 7 (o classificador dá de 0,81 a 1,00 de probabilidade máxima nos dez quadros). A de cima é uma dupla exposição.

    Por que a de pixels não passa. A interpolação é linear nos pixels: o quadro é a soma ponderada das duas imagens, então nenhum traço pode se mover, só apagar enquanto outro acende. Os dígitos ocupam uma superfície fina e curva em \(\mathbb{R}^{784}\), e a corda entre dois pontos de uma superfície curva sai dela. Por que a latente passa. A reta é nos códigos, e o decodificador é não linear: a reta vira uma curva em pixels, que desloca e deforma o traço em vez de misturar duas imagens.

    Os números descrevem isso, e em boa parte são a própria aritmética: no ponto médio em pixels, um pixel aceso numa só das imagens vale 0,5, então a área de tinta é a união das duas e só as sobreposições passam de 0,5. O resultado não depende da escolha do par. Em 500 pares de dígitos diferentes, sorteados na validação:

    500 pares Área de tinta (> 0,2) Traço forte (> 0,6)
    Imagens reais 125,0 93,7
    Suas reconstruções 135,3 91,7
    Pontos médios em pixels 182,1 43,9
    Pontos médios latentes 135,3 68,7

    O ponto médio latente tem a área de tinta de uma reconstrução (135,3 nos dois casos), embora perca traço forte (68,7 contra 91,7): é um traço só, mais borrado. E quem elimina a dupla exposição é o decodificador, não o KL: no controle com \(\beta = 0\), o ponto médio latente também é um traço só (área de 137,6), o que não mostra ganho do KL na interpolação, numa única semente. Onde o KL faz diferença grande é na amostragem.

    A latente não garante um dígito. Na Figura 6b, a reta de um 1 a um 0 (índices 2 e 3) passa, em \(t = 0{,}44\) e \(0{,}56\), por um rabisco com probabilidade máxima de só 0,37 e 0,24, contra 0,94 ou mais nos outros quadros. E nos 500 pares, 53,8% dos pontos médios latentes ficam abaixo de 0,9, contra 7,6% das reconstruções (parte disso é ambiguidade legítima, pois um ponto entre dois dígitos pode ser mesmo um meio-termo).

    Discussão

    O que o prior compra e quanto custa. Em \(d = 16\), tirar o KL melhora a reconstrução em 13,26 nats (67,15 contra 80,41), mas tira o prior da escala dos códigos: o classificador fica abaixo de 0,9 em 99,6% das amostras, contra 48,6%. A interpolação quase não muda.

    Limites das medidas. As figuras e as tabelas vêm de uma semente, a do enunciado. O classificador foi treinado em imagens reais e é aplicado a imagens borradas: os valores absolutos dependem dele, e só as comparações entre conjuntos decodificados interessam.

    Conclusão. O otimizador paga KL porque um código informativo devolve bem mais reconstrução do que custa, e 6,14 nats por nat em média. Esse pagamento produz um espaço de onde se pode amostrar, mas não perfeito: as amostras do prior caem também entre os grupos de dígitos, e o decodificador devolve médias. Com duas dimensões, o espaço fica visível, ao custo de 53,51 nats de reconstrução e da maior parte da variação dentro de cada dígito, um limite das dimensões, e não do KL.
